# ADR 0001: 望月京子 AITuber の現行構成と仕様

- 状態: 現行実装の記録（遡及 ADR）
- 記録日: 2026-10-23
- 調査対象: コミット `c427a42` のリポジトリ内の設定・実装・ドキュメント
- 確認方法: ソースの静的確認。学習、推論、GGUF 変換、配信の実行検証は含まない。

## 背景

後継・部分置換: [ADR 0026](0026-kyoko-awakening-in-pc.md)で人物の背景と目標を具体化した。以下は調査当時の記録として保持する。技術構成と他の人物設定は継続する。

このプロジェクトは、日本語のキャラクター「望月京子」を表現する言語モデルを学習し、ローカルで対話するためのシステムである。キャラクター用データで LoRA を学習し、Transformers で利用する経路と、モデルを変換して Ollama で利用する経路を持つ。

README には実装済みの機能、将来構想、過去のモデル名が混在している。そのため、本 ADR は現在の実装から読み取れる設計を基準として記録する。当時の比較検討や採用理由は記録がないため推定しない。また、この記録だけで将来機能や品質保証を新たに採用したことにはしない。

## 記録する設計

### 1. キャラクターは望月京子とする

設定データは [`data/character_profile.json`](../../data/character_profile.json) に保持する。

| 項目 | 設定 |
| --- | --- |
| 名前 | 望月京子 / Mochizuki Kyoko |
| 年齢・性別 | 32 歳・女性 |
| 性格 | 引っ込み思案で内向的。優しく遠慮がちで、自信なさげ |
| 一人称・口調 | 「わたし」。丁寧でやさしく、「あ、あの……」「えっと……」などのためらいを表す |
| 関心 | サーモンの寿司、アニメ・マンガ、かわいい雑貨、RPG・リズムゲーム、大きな犬 |
| 背景 | 突然 AITuber になり、その原因の記憶が曖昧 |
| 目標 | 配信を通じて自分を取り戻し、視聴者と心をつなぐ |

人格表現は学習データとプロンプトで与える。CLI はプロフィールから挨拶・終了挨拶などを読み込むが、生成時の人物紹介はコード内にも保持する。Ollama のルートにも独自の SYSTEM 設定がある。プロフィール全項目がすべての経路へ自動反映される構造ではない。

### 2. Qwen2.5 に LoRA を適用して学習する

根拠: [`config.yaml`](../../config.yaml)、[`train_lora.py`](../../train_lora.py)。

| 項目 | 現行の既定値 |
| --- | --- |
| ベースモデル | `Qwen/Qwen2.5-0.5B-Instruct` |
| モデルロード | 8bit 量子化、`device_map=auto`、float16 |
| LoRA | rank 16、alpha 32、dropout 0.1、bias なし |
| 適用層 | `q_proj`、`v_proj`、`k_proj`、`o_proj` |
| 学習方式 | PEFT の CAUSAL_LM、Transformers Trainer |
| 学習 | 3 エポック、学習率 `2e-4`、訓練・評価バッチサイズ各 4 |
| メモリ対策 | gradient checkpointing、fp16 |
| データ長 | 最大 512 トークン |
| 保存先 | `outputs/lora_model`（モデルと tokenizer） |

`--config` で設定ファイルを選択し、`--model` と `--epochs` で上書きできる。モデル全体の更新ではなく LoRA アダプターを学習する構成である。README 冒頭や学習スクリプトの説明にある「Qwen3」は、現在の既定値を示すものとして扱わない。

### 3. 学習データは instruction/input/output の JSONL とする

根拠: [`data/training/prepare_dataset.py`](../../data/training/prepare_dataset.py)、`LoRATrainer.format_instruction`。

- 挨拶・自己紹介、一般的な質問、配信中の対話の 3 種の元データを結合する。
- 各レコードは `instruction`、`input`、`output` を持つ。
- データ準備スクリプトを直接実行すると乱数 seed 42 でシャッフルし、90% を訓練、残りを検証に分割する。
- 調査時点の保存済みデータは訓練 127 件、検証 15 件。件数はデータ追加で変化するため固定要件ではない。
- 学習文字列は `### 指示:`、任意の `### 入力:`、`### 応答:` で構成する。
- 現行実装は入力部分を含むトークン列全体を教師ラベルにし、パディング部分だけを `-100` で損失計算から除外する。

### 4. 標準の対話経路は Python CLI とする

根拠: [`chat_interface.py`](../../chat_interface.py)、[`inference.py`](../../inference.py)。

処理の流れは、ユーザー入力 → 人物説明と直近履歴の構成 → 推論用フォーマット → tokenizer → ベースモデルと LoRA → 応答表示、となる。

- 推論時は `outputs/lora_model` が存在すればアダプターを適用する。存在しなければ警告を出してベースモデルだけで続行するため、起動成功は人格学習済みであることを保証しない。
- 共通推論の既定値は temperature 0.7、top-p 0.9、top-k 40、最大生成 256 トークン、repetition penalty 1.1。入力は 512 トークンで切り詰める。
- キャラクター用 CLI は最大生成 80 トークン、repetition penalty 1.2 に上書きし、人物説明と直近 5 件の対話を指示へ埋め込む。
- 入力が空ならスキップする。終了語、EOF、キーボード割り込みで対話を終了する。
- `chat_history.json` に時刻・ユーザー発話・応答を保存する。保存時は最新 10 セッションを残し、起動時は前回セッションの末尾 10 件を読み込む。通常対話は終了時に保存するが、デモ経路は保存処理を呼ばない。
- `LoRAInference.chat` の `context` 引数は現状では生成へ渡されない。履歴付き対話は `ChatInterface.generate_response` の経路で行う。
- `batch_generate` は分割単位ごとに 1 件ずつ生成する実装であり、複数入力の同時推論ではない。

### 5. Ollama は別の推論経路として用意する

根拠: [`convert_to_gguf.py`](../../convert_to_gguf.py)、[`setup_ollama.sh`](../../setup_ollama.sh)、[`Modelfile`](../../Modelfile)、[`ollama_test.py`](../../ollama_test.py)。

LoRA とベースモデルをマージし、llama.cpp を使う GGUF 変換を経て、`aituber-kyoko` として Ollama に登録する構成を用意する。既定の量子化指定は `q4_0`。変換スクリプトの生成・実行など複数段階があるため、Python スクリプトの起動だけで利用可能なモデルが完成するとは扱わない。

ルートの Modelfile は人格 SYSTEM、専用テンプレート、temperature 0.8、top-p 0.9、top-k 40、repeat penalty 1.1、コンテキスト長 2048 と停止文字列を定義する。変換処理は別途 Modelfile を生成するため、実際に登録するファイルを確認する必要がある。Transformers の設定・履歴処理との同一動作は保証されない。

### 6. 学習と評価はローカルのコマンドで実行する

根拠: [`package.json`](../../package.json)、[`run.py`](../../run.py)、[`test_model.py`](../../test_model.py)、[`requirements.txt`](../../requirements.txt)。

Python スクリプトを実体とし、npm scripts と統合実行スクリプトを入口として用意する。npm scripts の多くは Bash と `venv/bin/activate` に依存するため、Windows の PowerShell 単体でそのまま動くことは前提にしない。

評価スクリプトは基本応答、人格一貫性、境界入力、性能などを扱う。人格評価には文字列の一致率を使い、Transformers 側は 50%、Ollama 側は 30% を各ケースの成功基準にしている。これは簡易な診断であり、人間による品質確認や本番受け入れ条件の代替とはしない。README の速度・メモリ数値も、本 ADR では測定済みの保証値としない。

## 実装範囲と将来構想

| 領域 | 調査時点の範囲 |
| --- | --- |
| データ準備・LoRA 学習 | Python 実装あり |
| CLI 対話・履歴・推論 | Python 実装あり |

| デプロイ・監視・バックアップ | `tools/README.md` の予定内容 |

配信サービスとの接続、アバター描画、音声生成を含む自動配信システムが完成しているとは扱わない。

## 影響と制約

- 学習と推論を分離し、ベースモデルとアダプターの組み合わせでキャラクターを利用できる。一方、モデル変更時は学習時と推論時のモデル整合性を利用者が管理する必要がある。
- 人格が JSON、学習データ、CLI の固定文、Modelfile に分散しているため、設定変更時に不一致が生じうる。
- 会話記憶は短い履歴をプロンプトへ入れる方式であり、長期記憶や検索を行う実装はない。入力上限で履歴や発話が切り詰められることがある。
- GPU、量子化ライブラリ、Transformers、llama.cpp、Ollama の環境依存がある。依存の下限指定だけでは実行環境の完全な再現性は得られない。
- 会話履歴は平文 JSON で保存される。保存範囲・保持期間・公開時の取り扱いに関する運用方針は未決定である。

## 別 ADR で判断する事項

1. 人格設定の一元化と、学習・CLI・Ollama への反映方法。
2. 本番モデル、推奨環境、応答時間、人格品質の受け入れ基準。
3. 音声・アバター・配信連携の技術選定と処理順序。
4. 公開 API の契約、認証、同時実行、障害時の振る舞い。
5. 配信コメントの選択・不適切入力への対応・会話履歴の管理。

これらは現行コードの仕様確定とは切り離し、要件を決めてから採否と代替案を記録する。
